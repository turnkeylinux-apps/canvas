## Source and dependency decision

Debian packages are preferred. Debian Trixie supplies Node.js 20, PostgreSQL,
Redis and the native build libraries; Apache and Passenger come from the
inherited Rails appliance plan. Trixie renamed the XML Security runtime for the
64-bit `time_t` transition, so the package plan uses Debian's `libxmlsec1t64`
with `libxmlsec1-dev` and does not request the removed Bookworm package name
`libxmlsec1`.

Debian does not package Canvas LMS. The appliance therefore installs the
official Canvas production release identified by the `prod` branch at commit
`44bfdc264d5fe6a942ebdb5f10a0eb63ee04df3a`, whose source tree is
`dd2a9caa6afe683108a493a13c32340e1b3ac5e6`. The downloaded commit archive
must match SHA256
`2ca116f8a130b970c7b945fd547e760bdb8e7b8d0ea4c1c63f07222fd874009c`.
The commit is the official production merge for stable release 2026-04-22.

The official RCE API is likewise absent from Debian and is pinned to commit
`e076fe28a09f4e41058da0983b5ef2c809123d9f`, tree
`4a2e99c1efccf0011215bb074065a0859135a132` and archive SHA256
`1b36c2231c09d406053c92fde9d805211e538265e8d01827477a3ce9187c0495`.

Canvas requires Ruby 3.4.1 or newer within Ruby 3.4. The inherited TurnKey
Rails build installs Ruby 3.4 through its maintained ruby-build path. Debian's
`yarnpkg` is Yarn 4.1 and does not satisfy the Canvas Yarn Classic lock and
install contract. The inherited Rails build therefore installs Yarn Classic
from Yarn's signed official APT channel. The exact test refreshed only that
source, verified the signed APT metadata and found candidate `1.22.22-1`.
Bundler 2.6.7 and all Ruby, JavaScript and RCE dependencies remain locked by
the verified source trees.

The disposable gate creates the prior database and a preserved course, runs

Preparing this lifecycle gate found that the updater had run `pg_dump` under
the root operating-system account even though local PostgreSQL authentication
expects a database role of the same name. The passing candidate runs the dump
as the PostgreSQL administrator.

Canvas 2026-04-08 uses Switchman 4.2.4, which wraps `db:migrate` by enumerating
`switchman_shards`. A deliberately blank database does not yet contain that
relation because the predecessor's squashed baseline migration creates it.
The fixture therefore verifies baseline migration file
`20101210192618_init_canvas_db.rb` at SHA256
`3a53a2665099c09222d1bd96bdc236685c8222aa2073f8a17360dd4dc95abd9f`,
asserts the relation is initially absent, and invokes that exact baseline
through the underlying Rails migration context from a temporary Rake task.
Unlike `rails runner`, Rails 8.0.5's Rake environment disables application
eager loading unless the application explicitly opts in. The temporary task
rejects either Rake or application eager loading before it obtains the typed
baseline version and calls the migration context. It then requires the relation
and recorded baseline version to exist, rejects any later recorded version,
and returns to the official `db:initial_setup` task for the remaining schema
and initial data.

The lifecycle test exercises the normal user flow before replacing Canvas with
the predecessor, so Redis database 0 initially contains the current release's
settings and root-account cache. Recreating PostgreSQL alone invalidates those
cached database identities. The fixture now requires Redis `PONG`, clears only
database 0, requires `DBSIZE` zero, and then starts the predecessor migration
in a fresh Rake process. After the official initial-setup task it joins the
`default_account_id` and `site_admin_account_id` settings back to real account
rows and requires both matches before later migrations or updater apply.

The predecessor's official production Dockerfile performs a frozen Yarn
install and `canvas:compile_assets` before any runtime database migration. Its
`RegenerateBrandFilesBasedOnNewDefaultsPredeploy` migration explicitly says
that assets, specifically `gulp rev`, must run first. The fixture follows that
ordering with the predecessor's frozen lock, then invokes the official compile
task with API documentation, CSS, styleguide, Webpack, brand writes and full
locale generation disabled. Source-map processing is disabled for the same
fixture-only task. Those branches are not needed to construct the prior
database, while the task's unconditional `js:gulp_rev` branch still creates
the required predecessor manifest. The fixture requires a nonempty JSON object
containing at least one fingerprinted target before database bootstrap or
migration begins.
